# Detection evaluation report

The evaluator runs each rule against 13 isolated, labelled synthetic scenarios in `samples/evaluation_cases.json`. There are nine positive rule labels across the cases. The output is regenerated by `cd backend && ../.venv/bin/python -m scripts.evaluate` and saved as `docs/detection-evaluation.json`.

| Measure | Result on this corpus |
| --- | ---: |
| True positives | 9 |
| False positives | 0 |
| False negatives | 0 |
| True negatives | 108 |
| Precision | 1.000 |
| Recall | 1.000 |
| F1 | 1.000 |
| False-positive rate | 0.000 |

Each of the nine rules has one positive case and 12 negative cases. Four entire scenarios contain no positive labels; the remaining nine each contain one positive rule label. Thus 13 scenarios x 9 rules = 117 decisions, of which 108 are negative rule-scenario pairs. The negative cases include normal logins, repeated connections to one port, short DNS queries, and a large internal backup. These are **fixture checks**, not a valid estimate of field performance. Thresholds and cases were designed together; no independent real traffic or unseen attack dataset was used. The 1.000 values should not appear on a resume as real-world detection accuracy. The evaluator also returns passed/failed scenario counts and measured pure detection time for each scenario; these timings vary by machine and run.

To improve evaluation, collect authorized and anonymized network data from different environments, label cases independently, separate tuning and test sets, measure incident-level outcomes, and report uncertainty and false alerts per day.
